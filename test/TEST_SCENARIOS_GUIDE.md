# Test Scenarios Guide

This guide describes the types of tests you can run against the Wazuh infrastructure.

---

## Overview

All tests use the **same baseline infrastructure** (Wazuh server + agent in terraform/). Test-specific requirements (additional security groups, resources, configuration) are **generated by agents** in `test/terraform/` during the test and **deleted during cleanup**.

This approach keeps the baseline clean and lets each test define exactly what it needs.

---

## Available Test Types

### 1. Fresh Deployment (Baseline)

**Purpose**: Verify Wazuh server and agent deploy and communicate correctly.

**What deploys**:
- Wazuh server (manager + indexer + dashboard)
- Wazuh agent (auto-enrolled)
- Basic security groups

**When to use**:
- Testing new Wazuh versions
- Validating infrastructure changes
- Establishing baseline before testing features

**Typical duration**: 45 minutes  
**Cost**: ~$0.21

**Verification**:
```bash
ssh -i terraform/wazuh-test-key.pem ubuntu@<server_dns>
sudo systemctl status wazuh-manager wazuh-indexer wazuh-dashboard
sudo /var/ossec/bin/agent_control -l
```

---

### 2. Blog Post Testing (EOL Detection)

**Purpose**: Validate implementation of a blog post (e.g., EOL detection).

**How it works**:
1. Agent reads blog post/documentation
2. Agent generates required infrastructure in `test/terraform/`
   - Example: Security groups for external API access
   - Example: Custom rules file deployment
   - Example: Additional Python scripts
3. Deploy with `terraform apply`
4. Execute blog post procedures
5. Document findings
6. Cleanup: `terraform destroy && rm -rf test/terraform/`

**When to use**:
- Testing blog post implementations
- Validating custom integrations
- Verifying documented procedures

**Typical duration**: 60 minutes  
**Cost**: ~$0.32

**What agent generates**:
```bash
cat > test/terraform/generated-test.tf << 'EOF'
# Generated from: [blog post analyzed]
# Purpose: [test objective]

resource "aws_security_group_rule" "external_api" {
  # Allow external API calls needed by blog post
  ...
}

resource "local_file" "custom_script" {
  filename = "/tmp/custom-integration.py"
  content  = file("${path.module}/../requirements/custom-script.py")
}
EOF
```

### 3. Documentation Testing

**Purpose**: Validate official Wazuh documentation against live infrastructure.

**How it works**:
1. Agent reads Wazuh official documentation
2. Agent extracts documented procedures
3. Agent generates infrastructure to match doc requirements
4. Deploy and execute procedures from docs
5. Verify actual behavior matches documentation
6. Document discrepancies

**When to use**:
- Testing new Wazuh versions' documented procedures
- Identifying outdated documentation
- Validating API procedures
- Testing dashboard features

**Typical duration**: 60-120 minutes  
**Cost**: ~$0.42-0.84

**Test template**: See [DOCUMENTATION_TEST_TEMPLATE.md](DOCUMENTATION_TEST_TEMPLATE.md)

---

### 4. Upgrade Testing (4.14.6 → 5.0.0)

**Purpose**: Test the upgrade path from 4.14.6 to 5.0.0.

**How it works**:
1. Deploy 4.14.6 baseline
2. Generate upgrade-specific code in `test/terraform/`
   - Backup procedures
   - Upgrade verification checks
3. Execute documented upgrade procedure
4. Verify 5.0.0 operational
5. Test agent re-enrollment
6. Document upgrade findings
7. Test rollback if needed

**When to use**:
- Planning production upgrades
- Testing migration procedures
- Validating backward compatibility
- Verifying data preservation

**Typical duration**: 120 minutes  
**Cost**: ~$0.44

**Test template**: See [UPGRADE_TEST_TEMPLATE.md](UPGRADE_TEST_TEMPLATE.md)

### 5. Dashboard Access Testing

**Purpose**: Validate Wazuh dashboard UI/UX and features.

**How it works**:
1. Deploy baseline
2. Generate test code for:
   - Test data creation
   - Feature enablement settings
3. Access dashboard and test features
4. Capture screenshots/findings
5. Document UI/UX observations

**When to use**:
- Testing dashboard feature updates
- Usability testing
- Documenting UI behavior
- Screenshot capture for docs

**Typical duration**: 45 minutes  
**Cost**: ~$0.21

### 6. Agent Enrollment Testing

**Purpose**: Test agent enrollment protocols and communication.

**How it works**:
1. Deploy baseline (server + one agent)
2. Generate code for:
   - Additional agent deployments
   - Pre-auth key generation
   - Enrollment verification scripts
3. Test enrollment flows
4. Verify agent communication
5. Test agent updates/reconfiguration

**When to use**:
- Testing agent enrollment protocol changes
- Validating pre-auth key workflows
- Testing agent discovery
- Agent scaling tests

**Typical duration**: 45 minutes  
**Cost**: ~$0.21

---

### 7. Custom Scenarios

Any test not listed above can be created by agents:

1. Agent reads whatever documentation/blog post/feature description
2. Agent analyzes infrastructure requirements
3. Agent generates `test/terraform/` code with those requirements
4. Deploy, test, document, cleanup

This is the **design principle**: baseline stays clean, test needs are generated.

---

## General Test Workflow

All tests follow this pattern:

```
1. READ
   Agent reads documentation/blog post/requirements
   
2. ANALYZE
   Agent extracts infrastructure needs
   
3. GENERATE
   Agent creates test/terraform/generated-*.tf files
   
4. DEPLOY
   terraform apply (uses baseline + generated code)
   
5. TEST
   Execute documented procedures
   Follow TEST_SCENARIOS_GUIDE.md for the specific type
   
6. DOCUMENT
   Save findings to results/
   
7. CLEANUP
   terraform destroy
   rm -rf test/terraform/
   rm -rf results/
   
8. VERIFY
   Repository is identical to baseline
```

## Verification Rules (R1 & R2)

**R1: Never trust status, always verify with command**
- ❌ Don't: "Service is running" (assumed)
- ✅ DO: `sudo systemctl is-active wazuh-manager` → `active`
- ✅ DO: `curl https://localhost` → HTTP 302/200

**R2: Verify URLs before piping to shell**
- ❌ Don't: `curl -s URL | bash`
- ✅ DO: Check HTTP 200 first, then run

All test templates enforce these rules.
